## Root causes found in the code

### 1. Google sign-in blanks — two independent causes, both ours

**Popups are closed unconditionally.** `packages/hosted-browser/src/browser.ts:155`:

```ts
page.on("popup", (popup) => {
  void popup.close();
});
```

Yahoo's "Sign in with Google" opens Google's identity flow. We close it the instant it opens. The owner
sees nothing happen.

**Google is not reachable through our egress policy.** `packages/hosted-browser/src/provider.ts` allowlists
only Yahoo origins (`login.yahoo.com`, `guce.yahoo.com`, `s.yimg.com`, the fantasy hosts, and so on).
`installEgressPolicy` aborts anything else with `blockedbyclient`, so even a full-page navigation to
Google's identity endpoints is refused. The blank page is the abort.

So this is not a flaky integration: for an account whose Yahoo identity is a Google account, the hosted
browser **cannot** complete, by design and by omission. The local helper can, because it uses a real
browser with unrestricted network. That is why every successful link so far went through the helper.

This is a design decision, not a patch: allowing Google widens an allowlist we deliberately kept narrow.

### 2. Failed attempts become indistinguishable connection rows

A connection row is created when a hosted linking session starts, before any sign-in succeeds, and a
failure marks it disconnected (`HostedLinkingLive.complete` → `connections.cancelLinking`). Three
attempts therefore produce three cards, two of them dead, all titled "Yahoo connection", none carrying an
account identity or a failure reason, and none offering an action.

The card copy compounds it: a badge reading "Disconnected" above a sentence reading "This connection is
disconnected and no longer provides access."

### 3. The crosshair cursor is a class name

`apps/web/src/browser/shared-ui/BrowserFrame.tsx:65` sets `cursor-crosshair` on the streaming canvas. That
is the entire "janky" cursor complaint.

### 4. Pause expiry is rendered in provider-local time

The pause is defined against the provider's fantasy day, which is correct for the _rule_, but the UI
formats it in the provider's zone ("American Los Angeles time") rather than the viewer's. The rule should
stay provider-local; the display should be the browser's.

### 5. No-op activity is not collapsed

The team detail lists one row per hourly run. Because most runs verify a no-op, the one run that changed
something scrolls out of view. The owner's ask is to collapse the quiet ones and surface the events.

### 6. Feedback does not carry team context

"Report a problem with this team" navigates to the generic feedback form with no team reference, even
though the feedback record already has a `team_reference` column.

## Decisions taken

Settled by the owner on October 28 2026.

- **Voice**: keep the editorial voice, cut the swagger, **no emdashes**, plain human language, no
  jargon. Existing emdashes in product copy are to be removed as well.
- **Hosted browser**: the local helper is to be removed entirely, because it only works locally and has
  no place in a hosted product. Everything goes through the hosted browser, which means it must work for
  a Google-identity account before the helper is deleted.
- **Egress policy**: replace the static host allowlist with provider-independent protections. The owner's
  objection is correct: the allowlist carries a maintenance burden and fails silently. See the threat
  model below.
- **Failed attempts**: leave nothing behind.
- **Team context**: one line per team, and the list needs flair without becoming cards. To be explored
  with an Impeccable pass.
- **Toggles**: optimistic with a visible pending state and revert on failure.

## The egress threat model, as it stands

Three layers exist today, not one:

1. `--host-resolver-rules=MAP * ~NOTFOUND, EXCLUDE <allowed hosts>` — every unlisted hostname fails to
   resolve.
2. A request and websocket filter aborting anything outside the allowed origins.
3. Isolation: one-use owner-bound ticket, ephemeral profile destroyed afterwards, dialogs dismissed,
   downloads cancelled, new pages closed.

Ranked by whether the allowlist actually helps:

- **SSRF into our own network.** The real risk, and the **DNS blackhole** is what stops it, not the host
  list. It is provider-independent and needs no maintenance.
- **Our service used as a free headless browser.** The allowlist limits this; the ticket, owner binding,
  session lifetime and rate limits are the replacement.
- **A hostile page exploiting the Chromium we ship.** Not a real boundary; keeping Chromium current is
  the mitigation.
- **Session theft.** The allowlist does nothing here. The same-origin policy prevents another origin
  reading the provider's cookies. Capture-after-acceptance and profile destruction are what protect the
  session.

Therefore: keep the DNS blackhole and extend it to refuse private, link-local, loopback and metadata
addresses; allow public origins for the sign-in flow; keep the ticket, isolation, download and dialog
policy and capture rule; add a per-account session rate limit; and make any refusal name the host and be
recorded, so breakage is a specific reportable event rather than a blank page.

## Alternatives to the hosted browser, assessed

- **Yahoo OAuth** — the official Fantasy Sports API is closed to new applications and does not support
  lineup writes. Not available.
- **User pastes the session cookie** — provider cookies are HttpOnly, so this needs devtools. Not a user
  flow, and it teaches people to hand over session tokens.
- **Browser extension** — ruled out by the owner; per-browser and per-provider builds.
- **Local helper** — works, and is to be removed.

The hosted browser is the only viable hosted path.

## Decisions originally raised

These were the questions put to the owner.

### D1. Voice and copy

The substance is praised; the register is not. Three candidate directions, each applied to the same real
sentence so the difference is visible:

The current sentence, on the connections page:

> "Sign in through a temporary browser. Your password is entered on Yahoo's page; Lineupkeep keeps only
> the encrypted session."

**(a) Plain and procedural.** Drop the fragments, write in complete sentences, lead with what you do.

> "When you connect, a temporary browser opens so you can sign in to Yahoo directly. Lineupkeep never sees
> your password. It keeps only the session Yahoo issues, encrypted."

**(b) Sober product voice.** Same information, slightly more formal, no second person imperative.

> "Connecting opens a temporary browser session where you sign in to Yahoo yourself. Lineupkeep does not
> receive your password; it stores only the resulting session, encrypted."

**(c) Keep the editorial voice, remove the swagger.** Short lines stay, but no aphorisms, no slogans, no
headline fragments where a sentence belongs.

> "You sign in to Yahoo in a temporary browser, not here. Lineupkeep stores the session Yahoo issues —
> encrypted — and never your password."

My recommendation: **(c)**. The owner likes the aesthetic and dislikes the pretension; (c) keeps the
character and removes the swagger. The landing headline "Your lineup. Looked after." is the most
marketing-like line in the app and should go under any of the three.

### D2. Can the hosted browser reach Google?

- **(a) Allow Google's identity origins and stream popups.** Hosted linking works for Google-identity
  accounts. Cost: the egress allowlist grows beyond Yahoo, and we must handle multiple browsing targets,
  which widens the surface we deliberately narrowed.
- **(b) Detect and hand off.** Keep the allowlist narrow; when the provider redirects to an identity
  origin we cannot reach, stop, explain in one sentence, and hand the user to the local helper with the
  pairing code already prepared. Cost: the primary path becomes "primary for most, helper for Google".
- **(c) Make the helper the primary path** and treat hosted linking as the convenience for accounts that
  do not use an external identity provider.

My recommendation: **(b) now, (a) as a deliberate follow-up.** (b) is honest, ships quickly, and turns a
blank page into a clear next step. (a) is the right long-term answer if we want hosted linking to be
genuinely universal, but it is a security decision and deserves its own review.

### D3. What a failed link attempt should leave behind

- **(a) Nothing.** A connection row is created only when sign-in succeeds; the attempt lives in the
  hosted-linking session record, which already keeps history.
- **(b) A card that says what happened.** Status `failed`, the account identity if known, the reason, a
  timestamp, and a Remove action.

My recommendation: **(a)**, with (b)'s information surfaced from the attempt record where it helps. The
owner's complaint is that attempts pile up in a list of _connections_; the list should contain
connections.

### D4. Do connections need identity?

Whatever D3 settles, a connection card should say **which account** it is. That needs a provider account
label captured at link time. If the provider does not expose one we can use, we should say so and use a
distinguishing fact we do have (link time, team count, league names).

### D5. Teams list: list or cards, and how much context

- **(a) Keep the list, fix the copy and add a compact context line** — sport, record or standing, number
  of teams in the league, last run outcome.
- **(b) Cards** with the same information, more visual weight.
- **(c) List with a small standing/record block per row**, closer to the old app without its weight.

My recommendation: **(c)**. The owner explicitly does not want the old app's gaudiness and explicitly does
want some context. A list with one honest line of league context per team is the middle.

The context itself needs a data question answered: standings come from `get_league`, which costs a
provider read per team per page load. Options are to fetch on the team detail page only, or to cache a
daily snapshot. I would fetch on detail first and add a cached summary only if the list feels empty
without it.

### D6. Toggle feedback

The owner wants instant feedback on enable/disable/pause/resume. Optimistic update with a visible
in-flight state is the obvious answer; the question is whether we accept optimistic writes given that the
provider is not involved (this is our own state, so an optimistic update is safe and revertible). My
recommendation: optimistic, with a visible pending state and a revert on failure.

## Proposed plan, in order

**Phase A — the broken path and the pile-up (functional, no design debate needed)**

1. Detect an unreachable identity origin in the hosted browser, stop cleanly, explain, and hand off to the
   local helper with a prepared pairing code. Never leave a blank page.
2. Stop creating a connection row until sign-in succeeds.
3. Connection cards carry an account label, link time, team count, and a Remove action.
4. Fix the crosshair cursor.

**Phase B — voice (after D1)** 5. Rewrite the copy across landing, connections, teams, team detail, feedback, and empty/error states in
the chosen voice. Replace the landing headline.

**Phase C — teams (after D5)** 6. One component for team status, used by both list and detail, with the duplicated "automation on" badge
removed. 7. Add the compact context line per team; provider-local rule, browser-local display for pause expiry. 8. Optimistic toggles with pending state. 9. Back affordance on the detail page.

**Phase D — activity and feedback** 10. Collapse consecutive no-ops in recent activity, keeping the count and the events that changed
something. 11. Prefill the feedback form with the team reference when reporting from a team.

**Phase E — optional, needs D2(a)** 12. Allow Google identity origins and stream multiple targets, if we decide hosted linking should be
universal.

## What I would not change

The layout system, the type scale, the palette, and the general restraint. The owner's verdict is that
the simplicity is an asset. This is a voice, correctness, and information-density pass, not a redesign.
